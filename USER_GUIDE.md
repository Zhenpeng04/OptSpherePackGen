# SpherePackGen User Guide

SpherePackGen is a Python program for generating three-dimensional microsphere packing structures for optical scattering media. It is designed to produce particle coordinates, validate the generated geometry, compute basic structural descriptors, and export files that can be inspected or used in later electromagnetic simulation workflows.

The current version is the P0 / MVP implementation. It focuses on a reliable full workflow rather than advanced final-stage algorithms.

## 1. Main Functions

The current program can:

- read a YAML configuration file
- accept macro physical inputs in micrometers
- compute a suitable dimensionless cubic simulation box
- compute a suitable particle number when `num_particles: auto`
- generate several P0 structure types
- validate periodic-boundary non-overlap for hard-core structures
- calculate actual packing fraction, or Boolean-model nominal and covered volume fractions
- calculate nearest-neighbor distances
- calculate pair correlation function `g2(r)`
- calculate shell-averaged static structure factor `S(k)`
- export particle coordinates in dimensionless units and in real micrometer units
- export metadata, validation reports, analysis CSV files, optional HDF5 data, figures, and logs
- render one default perspective PNG view of the generated 3D sphere packing

## 2. Current Modeling Scope

The current version assumes:

- all particles are spheres
- all particles have the same material identity
- the simulation domain is a three-dimensional periodic cube
- hard-sphere non-overlap is the default geometric constraint except for `overlapping_random`
- internal generation uses dimensionless units with mean particle diameter equal to 1
- real output coordinates are exported in micrometers (`um`) by default

## 3. Structure Classification System

Each target structure is described by particle-size distribution and spatial order / correlation type. The density state is inferred automatically from the target volume-fraction input; users do not need to enter it.

### Axis A: Particle-Size Distribution

Supported or partially supported categories:

- `monodisperse`: all particles have the same radius
- `quasi_monodisperse`: small radius variation around the mean
- `continuous_polydisperse`: continuous distributions such as lognormal, truncated normal, uniform, gamma, Weibull/Rosin-Rammler, or a custom particle-size file
- `discrete_mixture`: several discrete particle-size species
- `imported_distribution`: radius samples loaded from an external file

### Axis B: Spatial Order / Correlation Type

P0 currently supports these practical generation routes:

- `periodic_crystal`: crystal structures such as SC, BCC, FCC, HCP
- `overlapping_random`: marked Poisson Boolean model of polydisperse overlapping spheres
- `hard_core_random`: non-overlapping random structure generated by variable-radius Poisson-disk, RSA, or force-biased dense routes depending on target packing fraction

Generic `hyperuniform`, `quasicrystal`, and `custom_target_correlation` are not implemented.

### Inferred Packing-Fraction / Density State

For non-overlapping structures, the program infers an internal density label from `physical.packing_fraction`:

| Packing fraction | Inferred label |
|---|---|
| `phi < 0.05` | `dilute` |
| `0.05 <= phi < 0.20` | `sparse` |
| `0.20 <= phi < 0.45` | `moderate` |
| `0.45 <= phi < 0.58` | `dense` |
| `0.58 <= phi <= 0.66` | `very_dense` |
| `phi > 0.66` | `crystal_dense` |

This inferred label helps select default algorithms and interpret validation results. It is saved in `metadata.json`.

For `overlapping_random`, the program uses the separate label `overlapping_nominal`. Users should enter the target covered volume fraction:

```text
physical.covered_volume_fraction = phi
```

The program then computes the nominal volume fraction:

```text
nominal_volume_fraction eta = -ln(1 - phi)
```

The nominal value can be greater than 1. It is the quantity used for particle-count and box-size calculation:

```text
eta = sum(sphere volumes) / box volume
```

The expected Boolean covered fraction is reported as `1 - exp(-eta)`. This follows the randomly distributed overlapping-spheres model described by Borman et al., where randomly placed spheres define the pore or inclusion phase and overlaps are allowed by construction.

## 4. Input File Format

The recommended user input is a YAML file. Users should mainly edit macro physical parameters and the desired structure class.

A minimal fixed rectangular random-packing example:

```yaml
project:
  name: my_rectangular_case
  description: Fixed rectangular random structure

structure:
  size_distribution: monodisperse
  spatial_order: hard_core_random

physical:
  mean_diameter: 0.3 um
  packing_fraction: 0.50

domain:
  type: periodic_box
  length: 2.0 um
  depth: 1.0 um

particles:
  num_particles: auto

size_distribution:
  type: monodisperse

algorithm:
  name: default

analysis:
  compute_g2: true
  compute_Sk: true
  bins: 80
  k_max_index: 5

validation:
  tolerance_phi: 1.0e-8
  tolerance_overlap: 1.0e-5

output:
  path: results/my_rectangular_case
  coordinate_unit: um
  formats: [csv, json]

runtime:
  random_seed: 12345
  log_level: info
```

## 5. Macro Physical Inputs

The main physical inputs are:

| Field | Meaning | Example |
|---|---|---|
| `physical.mean_diameter` | Mean particle diameter | `0.3 um` |
| `physical.packing_fraction` | Target particle volume fraction for non-overlapping structures | `0.45` |
| `physical.covered_volume_fraction` | Target Boolean covered fraction for `overlapping_random`; must satisfy `0 < phi < 1` | `0.70` |
| `domain.length` | Fixed lateral length, shared by x and y | `2.0 um` |
| `domain.depth` | Fixed depth along z | `1.0 um` |
| `physical.medium_thickness` | Legacy approximate cubic side length | `2.0 um` |

For the new `domain.length`/`domain.depth` inputs, dimensions are fixed. With
`particles.num_particles: auto`, the program selects an integer count using the
actual sampled particle volumes while retaining the configured mean diameter.
For monodisperse particles it rounds `phi * L^2 * D / particle_volume`. For broader
distributions it compares normalized sample-prefix volumes. The achieved density
and particle-count resolution allowance are reported separately. The allowance
is half the largest sampled particle volume divided by box volume; generated
volume must also match the resolved volume within `validation.tolerance_phi`.
For monodisperse particles this reduces to the half-particle rounding bound.
A box too small to support the requested density/particle sizes is rejected.

Provide both `domain.length` and `domain.depth`; do not combine them with legacy
`medium_thickness` or `box_size`. All axes are periodic, including depth. This
geometry describes a repeating medium rather than a slab with open surfaces.

Legacy `periodic_cube` configurations using `physical.medium_thickness` or
`domain.box_size` retain their original behavior: estimate the particle count,
then recompute the cubic side to match the requested density exactly.

In fixed-box mode, a manual count never changes box dimensions. Counts
inconsistent with particle sizes and target density are rejected with an
explanation. In legacy cubic mode, a manual count continues to determine a new
cubic side at the requested density; legacy thickness is a design reference.

Fixed-box SC/BCC/FCC/diamond crystals require equal lattice spacing along all axes.
Use `algorithm.parameters.unit_cells: [nx, ny, nz]` when needed. Arbitrary lengths,
depths and densities cannot all be imposed on an unstrained periodic crystal;
incompatible inputs fail explicitly. Fixed-box HCP is currently unsupported.
The GUI reports nearby compatible crystal dimensions at the chosen density.

Radial `g2(r)` stops at half the shortest dimension. `S(k)` uses wavevectors
`2*pi*(nx/Lx, ny/Ly, nz/Lz)`. A spherical average can hide directional effects in
thin or elongated structures. Non-overlap checks include a particle's own
periodic images.

Exports include `box_lengths` and `box_lengths_m` in metadata and `box_lengths`
in dimensionless HDF5. `config_replay.yaml` is a loadable configuration built from
the effective run settings; custom size files are archived under `inputs/`.
`config_resolved.yaml` remains a diagnostic parameter summary. Set an explicit
random seed for controlled experiments; when omitted, an actual seed is generated
and recorded. GUI downloads provide coordinates, metadata, a reusable configuration,
and a complete ZIP bundle including its input files and exact geometry snapshot.

The final resolved values are saved in:

```text
results/<case_name>/config_resolved.yaml
results/<case_name>/metadata.json
```

### Continuous Polydisperse Particle Sizes

For random media such as coatings or porous particle materials, use `continuous_polydisperse` when the particle sizes should be sampled from a continuous size distribution:

```yaml
structure:
  size_distribution: continuous_polydisperse
  spatial_order: hard_core_random

size_distribution:
  type: continuous_polydisperse
  distribution: lognormal
  CV_radius: 0.20
  min_radius_factor: 0.40
  max_radius_factor: 1.80
```

Supported continuous `distribution` values:

| Distribution | Main controls |
|---|---|
| `lognormal` | `CV_radius`, optional `min_radius_factor`, `max_radius_factor` |
| `truncated_normal` | `CV_radius`, `min_radius_factor`, `max_radius_factor` |
| `uniform` | `min_radius_factor`, `max_radius_factor` |
| `gamma` | `CV_radius` or `parameters.shape`, optional radius-factor limits |
| `weibull` | `parameters.shape`, optional radius-factor limits |
| `custom_file` | `size_file`, `file_values`, optional `file_column` |

For a custom file:

```yaml
size_distribution:
  type: continuous_polydisperse
  distribution: custom_file
  size_file: particle_sizes.csv
  file_values: diameter
  file_column: diameter_um
```

The custom file may be CSV, TXT, or DAT. It should contain one numeric particle-size column. Values can represent either `diameter` or `radius`; the program normalizes them to the requested `physical.mean_diameter`.

### Overlapping Random Boolean Media

Use `overlapping_random` when sphere centers should be independently distributed and sphere overlap is part of the model:

```yaml
structure:
  size_distribution: continuous_polydisperse
  spatial_order: overlapping_random

physical:
  mean_diameter: 0.3 um
  covered_volume_fraction: 0.70
  medium_thickness: 2.0 um

particles:
  num_particles: auto

algorithm:
  name: default

validation:
  require_non_overlap: false
```

For this structure, `algorithm.name: default` always selects `marked_poisson_boolean`. The program computes `eta = -ln(1 - covered_volume_fraction)` internally. The program also accepts old config values such as `uncorrelated_random` or `poisson`, but they are treated as compatibility aliases for `overlapping_random`.

## 6. Available P0 Generators

| Algorithm name | Purpose | Notes |
|---|---|---|
| `crystal` | SC/BCC/FCC/HCP/diamond-cubic crystal generation | Deterministic reference structures with vectorized unit-cell grid generation |
| `marked_poisson_boolean` | Polydisperse overlapping-sphere Boolean model | Independent centers, radius marks, overlap allowed |
| `poisson_disk` | Variable-radius Poisson-disk hard-core placement | Cell-list best-candidate sampling; default low-phi route for hard-core random structures |
| `rsa` | Random sequential adsorption | Good for sparse to moderate hard-core random structures |
| `force_biased` | Force-biased dense relaxation | Simplified Bezrukov/Jodrey-Tory-style route with outer-shell repulsion, outer-diameter-ratio contraction, dynamic Verlet cutoff shrinkage, and vectorized pair-force accumulation |
| `lubachevsky_stillinger` | Event-driven hard-sphere dynamic compression | Literature-aligned LS route with reduced-radius initialization, ballistic motion in a fixed periodic box, elastic collisions against an expanding contact surface, and linear radius growth to the target packing fraction |

If `algorithm.name: default`, the program chooses a P0 generator from `structure.spatial_order` and the relevant target volume fraction. Users can still override the default by setting a specific algorithm name.

Current default rules:

| Spatial order | Packing-fraction behavior | Default algorithm |
|---|---|---|
| `periodic_crystal` | all supported phi values | `crystal` |
| `overlapping_random` | all target covered fractions | `marked_poisson_boolean` |
| `hard_core_random` | `phi <= 0.18` | `poisson_disk` |
| `hard_core_random` | `0.18 < phi <= 0.34` | `rsa` |
| `hard_core_random` | `phi > 0.34` | `force_biased` |

For `hard_core_random` with `algorithm.name: default`, if the selected low- or mid-density hard-core placement route reaches its maximum attempts without placing all particles, the workflow automatically falls back to `force_biased`. If users explicitly choose `poisson_disk` or `rsa`, the program preserves that choice and reports the placement failure instead of silently switching algorithms.

For `force_biased`, the default parameter set changes at very high target packing fraction. When `physical.packing_fraction >= 0.60`, the generator uses stronger high-density defaults (`initial_radius_fraction: 0.65`, `outer_diameter_ratio: 1.08`, `relaxation_steps_per_stage: 800`, and `final_cleanup_steps: 2000`) unless the user explicitly overrides those parameters. Lower-density dense cases keep the faster baseline defaults.

The normal GUI exposes only the main force-biased controls: initial radius fraction, radius-growth stages, relaxation steps per stage, and contraction rate. Initializer budgets, outer-shell ratio, force scale, displacement cap, temporary overlap tolerance, Verlet skin, and final cleanup budget are advanced controls with defaults chosen from the current density regime.

The ordinary GUI route exposes `force_biased` as the internal middle/high-density non-overlapping random generator. `metropolis` remains available only as an explicit YAML/developer comparison algorithm and is not shown as a normal GUI choice. `lubachevsky_stillinger` can still be selected manually under `hard_core_random` when users want those specific non-overlapping generation routes. `lubachevsky_stillinger` initializes non-overlapping reduced-radius spheres, assigns random velocities, predicts pair collision times under periodic boundaries, applies elastic collision updates while all radii grow at `compression_rate`, and stops when the configured target radii are reached. Useful controls are `initialization`, `initial_radius_scale`, `warm_start_packing_fraction`, `warm_start_stages`, `warm_start_relaxation_steps_per_stage`, `warm_start_final_cleanup_steps`, `compression_rate`, `velocity_scale`, `max_events`, `mass_mode`, `event_backend`, `auto_exhaustive_particle_threshold`, `neighbor_skin_fraction`, `neighbor_velocity_safety_factor`, `neighbor_rebuild_fraction`, `max_attempts_per_particle`, `candidates_per_particle`, and `final_cleanup_steps`. The recommended `initialization: auto` uses reduced-radius Poisson-disk placement below `packing_fraction = 0.60` and switches to `force_biased_warm_start` at `packing_fraction >= 0.60`. In local N=500 checks, this warm-start route reached `packing_fraction = 0.60` and `0.62` with no final overlaps, while `0.64` remained too slow and failed to reach target within the tested event budget. The recommended `event_backend: auto` uses exhaustive pair scanning only for tiny systems (`N <= 2` by default), and a Verlet-neighbor priority queue for larger systems. `neighbor_rebuild_fraction` controls how much of the Verlet skin may be consumed before rebuilding the event list; the default `0.8` keeps a safety margin while avoiding overly frequent rebuilds. Users can still force `event_backend: verlet_heap` for scalable event scheduling or `event_backend: exhaustive` for conservative small-system debugging.

For large low-density `poisson_disk` runs, the default `candidates_per_particle` is 8 and `shell_outer_factor` is 1.0. This keeps the exact non-overlap check local to the cell-list neighborhood while avoiding the old all-particle candidate distance scan. Increase `candidates_per_particle` when a more evenly spread low-density configuration is more important than runtime.


Generic `hyperuniform`, `quasicrystal`, and `custom_target_correlation` are not implemented.

## 7. How to Run

Use Python 3.10 or newer. From a downloaded source checkout, install in a virtual
environment (Windows PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install .
```

On macOS/Linux, use `source .venv/bin/activate` to activate the environment.
A distributed wheel can also be installed with `python -m pip install /path/to/file.whl`.
After installation, open any user-owned working directory and run:

```text
spherepackgen examples --output examples
spherepackgen run examples/fcc.yaml
spherepackgen run /path/to/your_config.yaml
```

Packaged examples do not require a source checkout. Exporting examples never
overwrites existing files. Normal YAML output paths are relative to the current
working directory unless `output.relative_to_config: true` is selected.

CLI generation defaults to `--strict`: exit 0 indicates valid geometry and a
successful structure target; exit 2 indicates failed validation; exit 3 indicates
a valid candidate with an unmet target or generator warning; exit 1 indicates an
input/generation error. Use `--allow-candidate` to accept a geometrically valid
candidate as a batch job result. Metadata still reports its actual readiness.

## 7.1 Streamlit GUI Prototype

The project also includes a simple Streamlit graphical interface for creating a config, running generation, and previewing output figures.

Start it after installation:

```powershell
spherepackgen gui --workdir .
```

By default, the GUI saves CSV/JSON outputs, leaves `Save HDF5` unchecked, enables analysis plots and one perspective 3D packing view, and uses `Overlap tolerance = 1.0e-5`. Users can explicitly disable plots/views or enable HDF5 for runs where those choices are needed.

The workspace defaults to the directory where the command is launched.
`--workdir /path/to/workspace` selects another location; results, input cache and
history are stored there, independently of the Python installation directory.
History also remembers custom output destinations. Restart with the same
workspace to see previous runs. Use `--port 8502` for another localhost port or
`--headless` to skip automatically opening a browser.

The **Run** tab contains structure, particle size, fixed lateral length/depth,
particle count and the generation summary. **Advanced** contains distribution,
algorithm, output and analysis settings. **Results** retains the latest completed
run when current inputs change; its parameter snapshot identifies which inputs
produced the displayed coordinates and figures. Use the sidebar history selector
and **History** to inspect earlier runs without changing current parameters.

Every GUI generation uses a separate directory. Only files listed in that run's
`run_manifest.json` are displayed, preventing stale images or disabled exports
from a previous run from appearing. Legacy results without a manifest are labeled
as such. Download buttons preserve the current result view.

The worker reports workflow stages and supports **Cancel run**. Set **Run time
limit (s)** under analysis settings to bound the whole background generation;
the default is 600 seconds. Cancelling or timing out preserves earlier completed
results. Partial files in a failed run directory are not displayed as a completed
result.

S(k) detail presets use maximum reciprocal indices 5 (Quick), 10 (Standard), and
20 (Detailed). The GUI shows the particle–wavevector workload. Disabling plots
does not disable S(k) or g2 computation; their checkboxes control analysis.
The 3D view labels the number of displayed particles out of the complete count.

Fixed-box GUI crystals require monodisperse particles. Choose crystal cell counts
and click **Apply compatible crystal dimensions** to update L and D consistently
with the target density. HCP is available only through legacy cubic YAML input.
Candidates with a warning status require diagnostic review even if geometry
validation passes. Strict CLI mode gives them exit code 3.

The GUI lets you:

- enter macro physical parameters
- choose particle-size distribution
- choose continuous polydisperse distribution functions and upload custom particle-size files
- preview the current particle-size distribution while changing size parameters
- choose spatial-order type
- select `default` or a specific generator
- adjust advanced algorithm, analysis, and validation options
- generate a YAML config preview
- run the generator
- generate and view the default perspective packing image
- view `g2(r)`, `S(k)`, and radius-distribution plots
- inspect validation metrics and exported files

## 8. Output Files

Each run creates a result directory such as:

```text
results/my_fcc_case/
```

Important files:

| File | Meaning |
|---|---|
| `particles_dimensionless.csv` | Particle centers and radii in internal dimensionless units |
| `particles_real_units.csv` | Particle centers and radii in micrometers by default |
| `metadata.json` | Project metadata, resolved parameters, generator diagnostics, validation summary |
| `validation_report.json` | Pass/fail status and validation metrics |
| `config_input.yaml` | Copy of the user input config |
| `config_resolved.yaml` | Automatically computed parameters |
| `config_replay.yaml` | Effective settings, recorded seed, archived input paths and a fresh replay destination |
| `particles_snapshot.npz` | Exact dimensionless geometry, always stored regardless of CSV settings |
| `inputs/*` | Archived custom size input used for this run |
| `environment.json` | Software version, source fingerprint and numerical dependency versions |
| `run_manifest.json` | Output list, readiness flags and payload SHA-256 checksums |
| `run_bundle.zip` | Portable bundle containing the configuration, input snapshots and results |
| `analysis/g2.csv` | Pair correlation function |
| `analysis/Sk.csv` | Structure factor |
| `analysis/nearest_neighbor.csv` | Nearest-neighbor distances |
| `particles.h5` | Optional HDF5 geometry and analysis data, written only when `hdf5` is explicitly included in `output.formats` |
| `figures/*.png` | Basic analysis plots |
| `figures/packing_perspective.png` | Default perspective view of the generated 3D sphere packing |
| `logs/run.log` | Run summary |

### Reproduce or transfer a run

Download **Download complete result bundle** in the GUI and extract the ZIP on
the destination computer. Run:

```text
spherepackgen run /path/to/extracted/config_replay.yaml
```

The custom size input is read from inside the extracted bundle, and its SHA-256
is verified. Output is written to `replay/` beside the configuration; repeated
runs select new directories so earlier results are preserved. A normal user
configuration can opt into this behavior with `output.overwrite: false`.

The workflow generates and records an actual random seed when the input seed
is null. It does not modify the caller's Python configuration object.
`config_input.yaml` retains the original user settings; `config_replay.yaml`
contains the effective settings. Repeating an unseeded original input still
produces a new sample; use the replay configuration for the recorded sample.

To read the original geometry exactly without running generation again:

```python
from spherepackgen import load_snapshot

particles = load_snapshot("/path/to/extracted/bundle")
# Coordinates and radii are dimensionless. Convert to micrometers using
# the run's recorded mean diameter in micrometers if needed.
```

The snapshot is hash-verified before loading. Seed-based regeneration requires
the same software and numerical environment. The bundle records software,
environment and actual generator diagnostics. Identical optimized trajectories
across different platforms are not guaranteed.

The packing-view image uses a white background and light-blue particles. It is rendered with PyVista when available and falls back to matplotlib if PyVista rendering is unavailable. For large particle counts, the PNG view renderer uses a deterministic preview subset of at most 1000 particles and lower mesh resolution by default; coordinate CSV, JSON metadata, validation, and analysis outputs still use the full particle set.

For larger runs, nearest-neighbor distances and `g2(r)` are computed with periodic `cKDTree` backends instead of all-pair distance enumeration. In the GUI and config defaults, analysis plots and the single perspective 3D packing-view PNG are enabled by default, while HDF5 output remains optional and disabled by default.

## 9. How to Test the Program

Run:

```powershell
$env:PYTHONPATH="src"
python -m pytest
```

Expected result: pytest finishes without failures.

To re-check the Lubachevsky-Stillinger backend choice and neighbor-list tuning, run the lightweight benchmark script:

```powershell
$env:PYTHONPATH="src"
python scripts\benchmark_lubachevsky_stillinger.py --n 12 16 24 32 64
```

The script disables plotting and analysis, writes benchmark run outputs under `results/ls_backend_benchmark`, and prints JSON rows with elapsed time, selected backend, event count, neighbor rebuilds, and validation status.

## 10. Practical Notes

- FCC, BCC, SC, and HCP crystal structures are deterministic; changing `random_seed` will not change them.
- RSA can fail at high packing fraction because random insertion becomes difficult. This is expected behavior.
- `force_biased` is a simplified P0 force-biased algorithm, not a complete reproduction of the reference implementation or a rigorous proof of random close packing.
- `lubachevsky_stillinger` is the literature-aligned dynamic-compression option for users who explicitly want the LS protocol. It is not the ordinary default generator in this project; `force_biased` remains the practical default for medium/high-density random hard-sphere generation. LS results depend on compression rate, event budget, seed, and target density, and should not be described as a proof of random close packing or maximally random jamming.
- `metropolis` is retained as a developer/reference comparison algorithm for explicit YAML use; it is not part of the ordinary GUI route.
- The output box size may differ slightly from `physical.medium_thickness` because particle number must be an integer and crystal structures require compatible unit-cell counts.
- To create a new case, copy an existing YAML file, change `project.name`, `output.path`, and the macro physical parameters.

Reference for the overlapping-spheres model:

- V. D. Borman, A. A. Belogorlov, V. A. Byrkin, V. N. Tronin, V. I. Troyan, "The model of randomly distributed polydisperse overlapping spheres", arXiv:1302.5547.

- B. D. Lubachevsky, "How to simulate billiards and similar systems", Journal of Computational Physics 94, 255-283 (1991), arXiv:cond-mat/0503627.
